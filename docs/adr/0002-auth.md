# 0002 - Autenticación y sesiones

- Status: Accepted (actualizado 2026-08-29)
- Context: Tres planos: ops global, staff operativo del tenant, campus (alumno o docente). Cookies httpOnly y claims JWT. MFA requerido para superadmin.
- Decision:
  - Staff operativo: JWT Payload, cookie `payload-token`, host de administración, acceso a `/dashboard`.
  - Campus: JWT propio (`CAMPUS_JWT_SECRET`), cookie `campus_session` host-only, host de campus, claim `{ kind: 'student'|'teacher', id, tenantId }`.
  - Un docente de campus **no** es un User Payload. Crear ese User le daría el admin.
  - `campus_auth_tokens`: exactamente uno de `student_id` / `staff_id`.
  - Claims mínimas; middleware Next verifica tenant y plano; sin `DEV_AUTH_BYPASS` en prod.
  - Cookie campus: nunca `Domain=.akademate.com`. No mezclar `payload-token` en el host campus.
- Consequences: Dos emisores (Payload vs campus). Middlewares fallan seguro si falta `tenant_id` o si el `kind` no corresponde a la ruta. Invite/activate escriben el hash del sujeto correcto. Canon: [Master Spec §5.5 / ADR-016](../specs/AKADEMATE_MASTER_ARCHITECTURE_SPEC.md). Detalle P1: [plan 2026-08-29](../plans/2026-08-29-campus-identity-teacher-student.md).
